Live end-to-end demo

An AI assistant that acts on your behalf — safely.

The Acme Support Copilot is a chat assistant that calls real company APIs for a signed-in support rep. Tyk sits in the middle and makes sure every call carries who the human is and only the permissions this one action actually needs.

OAuth 2.0 Token Exchange · RFC 8693 Model Context Protocol (MCP) Keycloak identity

The one-sentence idea

When the assistant calls an API, the API doesn't see “a chatbot.” It sees the real support rep who is signed in — carried in a fresh token narrowed to exactly this one action. Read actions are allowed for everyone; sensitive actions like refunds are blocked unless the user is a supervisor.

Why it matters

The problem with AI agents calling your APIs

An agent needs to do things for a person — but if it just uses its own powerful key, you lose track of who the action was really for, and the agent can do far more than the person is allowed to.

🕵️

Lost identity

With a shared service key, every action looks like “the bot.” Audit and compliance can't answer “on whose behalf?”

🔓

Over-privilege

The agent's key can usually do everything. A read request and a refund request look the same to the backend.

✅

The Tyk way

Tyk swaps the user's login for an exchanged token that keeps the user's identity and is scoped to exactly this job.

Meet the cast

Two users, two permission levels

Permissions live in the user's identity as an entitlements claim. Tyk reads it at the MCP gateway and decides — before any token is minted — whether you're allowed this action. The assistant never decides what you're allowed to do.

You sign in

The support rep logs in with their company identity at Keycloak (OpenID Connect, with PKCE). The copilot holds that login token — never a shared admin key.

You ask the copilot to do something

“Look up customer C-1024.” The copilot turns that into a tool call and sends it to Tyk over MCP (the open standard for AI-tool communication).

Tyk checks your entitlements, then exchanges

At the MCP gateway, Tyk first checks the tool's required permission against your entitlements — if you're not allowed, it stops here with a 403, before minting anything. If you are, it swaps your login token — using RFC 8693 Token Exchange — for a fresh token aimed at the customer API, narrowed to just this action's scope. The new token keeps your identity (sub) while its azp records the gateway's client as the one that performed the exchange. This happens once, at the first hop.

The tool calls the real API

The MCP server runs lookup_customer and calls the downstream customer API with that exchanged token — passing the trace context along so the whole journey is one connected trace.

The API enforces the narrowed scope

The customer API (also fronted by Tyk) validates the exchanged token and checks its scope — which the exchange narrowed to exactly this action. Reads carry customers:read, updates customers:write, refunds refunds:write. A token narrowed for a read can't be replayed against a write — it gets a clean 403. Two independent gates: who you are at the proxy, what the token may do here.

You get an answer

The result comes back into the chat. The Delegation inspector on the right shows the before/after tokens so you can see your identity survive the hop while the audience and scope shrink to the one action.

How caching keeps it fast

The first call does the full IdP round-trip. Identical follow-ups are served from memory in sub-milliseconds — with a safety margin so a token is never handed out at its expiry.

Exchange-result cache

Caches the exchanged token per subject + target.

Cache key — hover a part
issuerThe IdP that signed the inbound token — a sub is only unique within its issuer. | subThe signed-in rep (e.g. alice) — the sub claim, or a hash of the raw token when absent. | apiIDWhich Tyk API matched — keeps caches from different APIs separate. | audienceThe downstream the token is minted for, e.g. api.acme.internal. | scopesSorted, space-joined requested scopes — a different scope set is a different token. Each tool's scope gets its own cache line. | providerThe configured exchange provider name.

TTL = min(token lifetime, inbound token's remaining life) − safety margin

≈ 25s served from cache
margin

The amber slice is trimmed so an expiring token is never served.

Single-flight on a miss

Concurrent first-misses for the same key are coalesced — a burst of identical requests triggers exactly one IdP call; the rest wait for its result.

🔑
The key is built from non-secret config only — the client secret is never part of any cache key.

The cache mode here is derived: the TTL follows the shorter of the exchanged token's life and the inbound token's remaining life, capped by maxTimeout (30s) minus the safetyMargin (5s).

📊
A cache hit records no IdP latency and increments a separate cache-hit counter (never a fake "success" outcome) — so the dashboards reflect real IdP load, not cache reads.
The environment

How the end-to-end demo is wired

Six moving parts, all running locally, behaving exactly like a production setup.

🪪

Keycloak Identity Provider

The enterprise IdP, running inside this compose stack with the realm auto-imported. It logs users in, holds their entitlements, and performs the standard token exchange.

💬

Copilot chat this app

A small web app + back-end that holds the user's login and speaks MCP to Tyk using the official Go SDK. It never sees the exchanged token.

🛡️

Tyk — MCP proxy acme-mcp-proxy

Fronts the AI tools. Authenticates the user, gates each tool against the user's entitlements (before minting anything), runs the RFC 8693 exchange, caches the result, and forwards the tool call.

🛡️

Tyk — resource API acme-api

Fronts the customer backend on a custom domain (api.acme.internal). It only validates and enforces scope — read vs refund — and returns OAuth challenges on denial.

🧰

MCP tool server mock backend

Exposes four tools — lookup_customer, update_customer, recent_orders, issue_refund — and calls the resource API with the exchanged token on your behalf.

📊

Observability OTel · Grafana

Every request emits a trace, metrics, and logs, collected into Tempo, Prometheus and Loki and viewed in Grafana — all joined by one trace id.

Tyk features on show

What Tyk is doing under the hood

🔄

OAuth 2.0 Token Exchange (RFC 8693)

The headline feature. Tyk swaps the inbound user token for an audience-scoped one that keeps the user's sub — the downstream API sees the person, not the bot.

🤝

Auditable caller (azp)

The exchanged token's authorized party names the gateway's exchange client — every downstream call records which client acted, without leaking who beyond sub.

🧩

Native MCP gateway

Tyk understands MCP/JSON-RPC: it routes tool calls, applies auth and scope per tool, and treats the AI surface as a first-class API.

🎯

Two-gate scope enforcement

Each tool/endpoint declares the scope it needs — customers:read, customers:write, refunds:write. The proxy checks it against the user's entitlements (who you are); the API checks it against the token's narrowed scope (what this token may do). Two independent gates.

⚡

Exchange caching

The exchanged token is cached briefly (~25s here) so repeat calls skip the IdP round-trip — fast, with a safety margin so a token is never served at its expiry.

🔐

OAS-native JWT / OAuth2 auth

APIs are defined as OpenAPI with Tyk security schemes — JWT validation against Keycloak's JWKS, plus a custom domain for the resource API.

🛰️

OpenTelemetry, end to end

Traces, metrics and structured logs for every exchange — outcome, provider, cache hit/miss, IdP latency — with no tokens or raw identities ever leaked into telemetry.

🧵

MCP trace-context bridge

Tyk reads the agent's trace id from the MCP message body so its spans join the agent's trace — the whole journey is one picture, not disconnected fragments.

See everything

One request, one trace

Because the trace context flows through every hop, a single tool call shows up as one connected trace — from the chat, through Tyk's exchange and the IdP round-trip, into the customer API and back.

🧭

Traces · Tempo

Watch the request flow through every component, see the exchange decision, and spot exactly where time is spent (or saved, on a cache hit).

📈

Metrics · Prometheus

Exchange volume by outcome and provider, plus IdP latency — the numbers an operator watches to know the feature is healthy at scale.

📜

Logs · Loki

One structured line per exchange decision and per request, carrying the same trace id — so you can pivot from a log straight to its trace.

🔒
Privacy by design: telemetry never contains a token value, a raw user identity, or a hash of one. The only identity recorded is the authorized party (azp client ids) — enough to see which client drove the exchange, never which user.
