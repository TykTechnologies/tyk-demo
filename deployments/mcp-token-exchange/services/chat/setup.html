Under the hood

How Keycloak and Tyk are wired together

The technical companion to the plain-English walkthrough. This is exactly what's configured in the identity provider, the gateway, the chat client, and the observability stack — and what travels on the wire during the RFC 8693 exchange.

The deployed design — one exchange, at hop 1

# alice signs in at Keycloak (auth-code + PKCE)
alice ──▶ Chat (MCP client)   tokenSSO: aud=tyk-mcp-gateway  sub=alice  scope=customers:all  entitlements=customers:read
        │  MCP tool call + Bearer tokenSSO
        ▼
   Tyk · acme-mcp-proxy   validate JWT → per-tool entitlement check → RFC 8693 EXCHANGE
        │  exchanging client = tyk-mcp-gateway   audience = api.acme.internal   scope = per tool
        │  Keycloak mints: aud=api.acme.internal  sub=alice  azp=tyk-mcp-gateway  scope=customers:read
        ▼
   Mock MCP server   tool runs, replays the exchanged token (forwards traceparent)
        ▼
   Tyk · acme-api (@ api.acme.internal)   VALIDATE-ONLY → enforce scope (read vs refund)
        ▼
   httpbin /anything   echoes the bearer → chat decodes & shows the chain
ℹ️
This is impersonation-style exchange (RFC 8693 without an actor token): the exchanged token keeps the rep's sub while its audience and scope are re-pointed at the one downstream action. The gateway's exchange client is recorded as azp — the auditable "which client performed the call" marker. Keycloak's standard token exchange does not mint an act (delegation) claim. The resource API never exchanges; it only validates.
First, the vocabulary

Keycloak concepts & how they connect

Keycloak models identity as a few building blocks inside a realm. Here's what each one is, and how they wire together to shape a token.

ConceptWhat it isIn this demo
RealmAn isolated tenant that contains everything below — users, clients, scopes. Its URL is the token iss.acme → http://acme-keycloak:8280/realms/acme
Client
(= OAuth client)		An application that requests (or is the target of) tokens. Public clients log users in; confidential clients authenticate with a secret.acme-support-chat, tyk-mcp-gateway, api.acme.internal
Grant / flowHow a client gets tokens: standard flow (auth-code login), token exchange (swap one token for another — a per-client capability toggle since Keycloak 26.2).PKCE · RFC 8693
Client scopeA reusable bundle of a scope name + protocol mappers. Default scopes always apply; optional ones apply when requested in scope=.customers:read · refunds:write · entitlements
Protocol mapperA rule on a client scope that computes a claim — map a user attribute, stamp an audience, emit sub.entitlements, audience, sub mappers
AudienceWho a token is for (aud). In Keycloak an audience is a client; audience mappers make it reachable.tyk-mcp-gateway → api.acme.internal
UserA human identity in the realm, with built-in fields and custom attributes.alice, bob
User attributeA custom field on the user record; a mapper turns it into a token claim.entitlements (string)
GroupA collection of users — org modelling and coarse boundaries.acme-support, acme-supervisors

How they connect

REALM (tenant)
 ├─ Clients       ──attach──▶ Client scopes (default | optional)   // what a token FROM this client contains
 ├─ Client scopes ──define──▶ Protocol mappers                     // claims: entitlements, aud, sub…
 ├─ Users         ──have──▶ attributes (entitlements)
 │                       └─▶ flow into token claims via the user-attribute mapper
 └─ Groups        ──contain──▶ Users          // org structure / boundaries
🔑
The key chain for this demo: a user (alice) carries an attribute (entitlements); the chat client logs her in and its scopes stamp entitlements and aud=tyk-mcp-gateway into the SSO token. The exchange — performed by the tyk-mcp-gateway client — retargets the token at another client (api.acme.internal) with the one scope the tool needs. Tyk enforces entitlements at the proxy and the narrowed scope at the API.
Identity provider

Keycloak configuration

Realm acme, running inside this compose stack and created entirely by keycloak/realm-acme.json (--import-realm) — no console clicking. Admin console: acme-keycloak:8280 (admin / admin).

Clients

ClientTypeFlowRole
acme-support-chatPUBLICauth_code + PKCEThe chat / MCP client — users log in here.
tyk-mcp-gatewayCONFIDENTIALtoken_exchangeThe client Tyk authenticates the exchange with. Standard token exchange enabled.
api.acme.internalAUDIENCE-ONLY—Exists to be the exchange's audience — Keycloak audiences are clients.

Constraints found live: Keycloak's standard token exchange only accepts a subject token whose aud includes the exchanging client (hence the mcp-gateway-audience mapper on the chat), and only honours an audience the exchanging client's scopes can produce (hence the acme-api-audience mapper on tyk-mcp-gateway). It ignores the RFC 8707 resource parameter.

Per-user authorization — the entitlements claim

Each user's allowed actions live in a custom user attribute entitlements, mapped straight into the token and carried across the exchange. Tyk's per-tool scope check at the MCP proxy reads this claim — not scope — so the gate is about the person, before any token is minted.

alice.entitlements = "customers:read"                                // update / refund → denied (403)
bob.entitlements   = "customers:read customers:write refunds:write"  // everything → allowed

Users & groups

  • Users: alice (group acme-support) and bob (acme-support + acme-supervisors), password Acme-Demo-2026!. Groups model the boundary; the entitlements claim is what's enforced.
  • Verify headlessly: keycloak/kc-verify.sh mints alice's token and replays the exact exchange, printing the before/after claims.
⚠️
Impersonation, not delegation: RFC 8693 also defines an optional act claim for delegation chains (via an actor token), but Keycloak's standard token exchange keeps the subject's sub and records the exchanging client only as azp. If your compliance model needs a cryptographic act chain, that is IdP-dependent (Ping and Curity mint it; Keycloak, Okta and Auth0 do not).
Gateway

Tyk configuration

Two OpenAPI definitions with Tyk extensions, applied via the Dashboard API by the deployment's bootstrap.sh — MCP defs to /api/mcps, OAS defs to /api/apis/oas, IDs injected dynamically (no static IDs).

acme-mcp-proxy the doer

  • Listen /acme-mcp/ → upstream the MCP server.
  • JWT validated against Keycloak JWKS; identity from sub.
  • scopeCheck.claimNames: ["entitlements"].
  • tokenExchange provider keycloak, client tyk-mcp-gateway, defaultTarget.audience: api.acme.internal.
  • cache: derived, maxTimeout 30s, margin 5s (~25s).
  • Per-tool security + exchange.enabled — each tool narrows to its own scope, inferred from its security requirement (union of alternatives). This demo omits exchange.scopes to demonstrate that inference; set it to pin the outbound scopes explicitly, with the provider's defaultTarget.scopes as the last fallback.

acme-api the guard

  • Custom domain api.acme.internal (= the exchange audience).
  • Upstream httpbin (the base deployment's, echoes the bearer).
  • Same JWKS validation; scope source is the token's scope claim.
  • No tokenExchange — validate-only.
  • Per-operation scopeCheck.enabled: true: customers:read on GETs, customers:write on the update, refunds:write on the refund → real 403 insufficient_scope.

Two claims, two gates — why a token without customers:read in its scope is accepted

The SSO token arrives with scope: openid customers:all and yet a tool requiring customers:read admits it. That is by design: the two gates authorize against different claims.

  • Front door (acme-mcp-proxy): "may this user do this?" Its scope check is configured with scopeCheck.claimNames: ["entitlements"], so the tool's required scope is looked up in the token's entitlements claim — a per-user attribute Keycloak stamps into every token (alice: customers:read; bob adds customers:write refunds:write). The incoming token's scope claim is never consulted here — customers:all is just the OAuth consent umbrella the chat requested at login, not a permission the gateway trusts. This is also why alice's refund is rejected before any exchange happens: refunds:write is not in her entitlements.
  • The exchange: mint a capability. Keycloak grants the requested narrow scope not because it was in the subject token's scope, but because it is among the tyk-mcp-gateway client's optional client scopes and the subject token's aud authorizes that client to exchange it.
  • Back door (acme-api): "may this token do this?" The resource API checks scopeCheck.claimNames: ["scope"] — there the actual scope claim of the exchanged token must contain the operation's scope. It never sees the broad SSO token at all.

entitlements = what the user may do (checked per tool at the proxy) · scope = what this specific token may do (narrowed by the exchange, enforced at the API).

What makes a request actually pass

  • JWT auth needs a policy. A small acme-demo-default policy grants access to both APIs; the deployment's bootstrap.sh resolves its id and injects it into each scheme's defaultPolicies. Without it, JWT auth returns 403 Access disallowed.
  • Token exchange override is explicit. The provider's enabled: true activates it; the per-tool exchange narrows the request to the scopes inferred from that tool's security requirement (or to exchange.scopes, when set).

Token-exchange client auth (proxy → Keycloak)

clientAuth:    method=client_secret_basic   clientId=tyk-mcp-gateway
defaultTarget: audience=api.acme.internal   scopes=[customers:read]
cache:         mode=derived   maxTimeout=30s   safetyMargin=5s
RFC 8693

The exchange, on the wire

What Tyk POSTs to Keycloak's token endpoint for one tool call (Basic auth = tyk-mcp-gateway creds):

POST /realms/acme/protocol/openid-connect/token        Authorization: Basic <tyk-mcp-gateway>
Content-Type: application/x-www-form-urlencoded

grant_type          = urn:ietf:params:oauth:grant-type:token-exchange
subject_token       = <alice's SSO JWT>
subject_token_type  = urn:ietf:params:oauth:token-type:access_token
audience            = api.acme.internal
resource            = api.acme.internal   // RFC 8707 companion; Keycloak ignores it
scope               = customers:read

Keycloak returns an access token with sub=alice, aud=api.acme.internal, azp=tyk-mcp-gateway and scope=customers:read. Tyk caches it (~25s), swaps it onto the Authorization header, and forwards.

Client

The chat application

  • Go back-end-for-frontend holding the user session; it never sees the exchanged token.
  • Login: OIDC auth-code + PKCE against Keycloak, with prompt=login so you can switch between alice and bob. The browser is redirected to the host-published Keycloak (acme-keycloak:8280); the code→token POST runs over the compose network (keycloak:8080) — the pinned KC_HOSTNAME keeps the issuer identical on both paths.
  • MCP client: the official go-sdk (StreamableClientTransport); a custom RoundTripper injects the user's bearer.
  • Tracing: a span per tool call, with the W3C trace context injected into both the HTTP traceparent header and the MCP body's params._meta (SEP-414) — so Tyk and the downstream join the agent's trace.
  • UI: a chat surface (left) for the conversation, a Delegation inspector (right) that decodes the SSO vs exchanged token and shows the raw upstream echo.
Telemetry

Observability stack

The gateway exports OpenTelemetry over gRPC; a self-contained collector fans signals out to three stores.

// tyk gateway config (opentelemetry block)
opentelemetry: { enabled: true, exporter: grpc, endpoint: acme-otel-collector:4317,
                 context_propagation: tracecontext, sampling: AlwaysOn,
                 metrics: { enabled: true, endpoint: acme-otel-collector:4317 } }
// per-API: server.detailedTracing.enabled = true  (spans)
//          server.detailedActivityLogs.enabled = true  (analytics → pump)
// OTel Collector pipelines
traces  → Tempo      (:3200)
metrics → Prometheus (:9090, remote-write)
logs    → Loki       (:3100)        view all in Grafana (:3001)
  • One trace per request: chat span → the gateway's exchange span (attrs: provider, outcome, cache_status) → IdP POST (absent on a cache hit) → acme-api → upstream.
  • Metrics: tyk.oauth2.exchange.requests (outcome × provider), …duration, and the separate …cache_hit counter.
  • Logs: the gateway console is tailed on the host (loki-tail.py) into Loki — Docker Desktop can't live-tail a host file from inside a container. Every exchange line and access-log line carries the same trace_id.
  • Privacy: no token values, no sub/jti in telemetry — only the non-PII client identifiers (azp), and only in logs + audit.
